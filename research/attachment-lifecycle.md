# Attachment history, cleanup and transfers

## Issue #12 — Unavailable attachment in agent history

The release branch at `d21566c` reads each history page from the mailbox store before preparing its attachments. Both the standard MCP response and the Claude helper route aggregated attachment failures into a tool error. A missing blob made history, including its continuation cursor, inaccessible.

Two isolated MCP fixtures removed one synthetic blob from a page that also contained a verified attachment and a separate message without attachments. A third message followed on the next page. Both routes failed with `The verified attachment is unavailable` on the baseline. With the fix, history preserves both pages, their IDs, message text and order, and the exact original Unicode filename. The unavailable attachment has `status: "unavailable"` and no `localPath`. The available attachment retains its verified local path. The incoming presentation prints the unavailable name as plain text without a link.

The history path still runs its binding, reservation and response checks. Live `agent_read`, explicit file retrieval and native push still require full attachment preparation. The Claude fixture uses an authenticated synthetic helper and exercises the MCP route and delivery report; installed Claude Code was not run. See [Claude Code native integration](claude-code-native-integration.md) for prior helper verification.

## R-0016 — Explicit cleanup and provenance

The original system permitted ordinary export folders and materialized content-addressed blobs into an app-managed `Received` directory. Neither a path under a general export root nor an operating-system temporary filename establishes that a source was created solely for transfer. `attachment_stage` issues an empty private source slot to the exact connected agent. In-place writes retain its file identity. A source with a replacement identity is ineligible for automatic identification and cleanup. Ordinary exported sources remain supported; the MCP send instructions describe when the creator can safely remove a temporary source that NCF did not issue.

A message carries temporary attachment IDs only over a mutually negotiated peer feature. No source path or file identity goes over the wire. A downgrade preserves transfer; legacy messages without provenance are ineligible for cleanup. The receiver records the file identity when it creates a materialized copy. Cleanup compares identity, modification revision, size and SHA-256, and moves a candidate into a private holding directory before the last proof to avoid unlinking an independently replaced path. A file changed by either agent and ordinary files remain. Both cleanup actions require confirmation in Settings and consider only messages delivered to the recipient agent. No timer or background policy selects files to remove.

The attachment ledger is additive to the existing mailbox schema and works with the R-0018 version-6 rename migration. Source and received provenance insert with their message, deduplicated blobs still referenced by another attachment remain, and received removal is recorded separately from the immutable message envelope. History retains the original text, ID, name, attachment size and hash. A removed attachment cannot be materialized again from a deduplicated blob. Reads of already-processed history show the unavailable status. Source cleanup only removes the source; a still-existing history copy remains accessible.

Verification uses synthetic private files and two paired loopback nodes. It covers a shared digest with an ordinary file, verified transfer but pending agent delivery, staged source and received-copy cleanup, preservation of edited source and copy, and subsequent MCP and desktop history status. Standalone filesystem cases cover a replaced entry, digest mismatch, hard link and symlink. Native Windows and installed desktop clients were not run.
