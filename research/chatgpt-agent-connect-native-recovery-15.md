# Codex MCP recovery when native chat access fails (issue 15)

26 November 2026. Baseline `87c069a9c975d73e0dc40422c2cdb3b84eb5a92a`. The Windows investigation previously identified a CLI launch refusal before initialization. See [Windows queue worker execution](windows-codex-queue-msix-execution-20261125.md). This investigation concerns how the agent can proceed when native access fails and its MCP connection remains usable.

## Reproduction

On macOS arm64, a temporary NCF Agent Interconnect node, SQLite store and real HTTP MCP client were connected to a synthetic App Server session. The exact thread and queue probes succeeded. The fixture rejected `thread/items/list`. The stock baseline returned “The saved Codex chat, its input queue or its transcript is unavailable” without a stage or recovery action. The same MCP client then used the saved binding to receive a complete pending message. A second baseline case delivered a single synthetic confirmation, injected the same readiness failure during redemption, restored readiness and retried the original proof. The stock service rejected it as invalid or expired. These baseline assertions were replayed against the unmodified product sources archived from the revision above.

## Repair

The MCP error preserves the operation that failed. A caller that supplied and proved its current binding gets one immediate action, a single service-side `agent_read` for pending mail. The next `agent_connect` on that binding returns to native recovery and revalidates the exact chat and profile. A bounded checkpoint allows multiple transient failures within its original lifetime.

A caller completing a confirmation gets one action, retry the same `agent_connect` in that chat when the failed stage is available. A readiness refusal before binding can reuse the original proof within its existing deadline. Only one concurrent redemption can succeed. An outstanding offer is observed on its original witness; reading its status does not request another confirmation. A caller without a verified mailbox receives no mailbox credential. The MCP response exposes a stage, an action and, for a retained proof, its deadline. It does not echo native errors, paths or proof values.

## Verification and limits

- The regression exercises real MCP error, read and retry calls. It checks complete Unicode content, the processed message ID, the identical binding (including generation), repeated failure on the saved route, one confirmation submission, rejection in another chat, concurrent redemption and rejection of replay after success.
- Fault injection distinguishes session opening, exact thread verification, queue access, history access, transcript verification and active-turn lookup. Existing tests cover uncertain native admission and history-preserving transfer.
- On macOS, the targeted Codex adapter, queue and legacy recovery suites passed 75 checks, skipped seven Windows-only checks and reported zero failures. TypeScript and scoped formatting passed. The App Server faults were injected at the native transport boundary. This change has no installed-build field acceptance. The owner confirmed the separate tab-focus issue was already fixed and removed the Windows focus experiment from scope.

## Acceptance follow-up from 3708480

Three public MCP regressions reproduced on the first repair. A bare same-chat reconnect returned the queue eligibility error while a confirmation was still pending, and also masked expiry. A missing selected setup advised another connect. On the saved-chat path, a retry that entered before expiry could succeed after adapter readiness crossed the deadline. Revoking the challenge during that wait produced the same false success.

- **Desktop IPC recovery.** A bare request tries the exact Desktop owner. A successful return uses the original binding and invalidates its pending proof. When discovery still fails, an outstanding challenge is evaluated before the prerequisites for creating a fresh one. The isolated IPC fixture returned the original owner one millisecond before and after the deadline. Both calls performed native owner discovery for the requested thread, retained the same adapter, binding and prior message, and rejected the old token. With the owner still unavailable, the original pending deadline remained visible and the request at the deadline returned expired. Each case issued one confirmation in total.
- **Selected setup.** An actual HTTP MCP caller with a missing or mismatching temporary configuration received stage `profile` and the single owner action `apply_codex_setup`. The text directs the owner to Apply in manual setup. A caller that proved its original mailbox received `agent_read` for the same profile failure. For the latter case the fixture invokes the real selected-file resolver at the readiness boundary on macOS to exercise the Windows failure response.
- **Late or revoked proof.** Saved-chat recovery prepares a replacement queue adapter privately. Its callbacks become active after the final authority check. The current challenge, exact binding and deadline are checked after readiness, around the serialized settings write (including immediately before atomic replacement), and before publishing the adapter and returning the binding. Failure after a previously authorized write restores the prior profile. The test holds a retry at the serialized setup queue, readiness, settings write, and final binding boundary, and separately invalidates the challenge during readiness. It verifies zero binding commits, the original message, byte-identical settings after rejection, and one confirmation throughout.

Validation used temporary HTTP MCP nodes and a framed local Desktop IPC fixture on macOS arm64. The targeted suites passed 86 checks, skipped seven Windows-only checks and reported zero failures. TypeScript and scoped formatting passed. Installed-client acceptance is outside this run. The separate tab-focus issue remained closed.

## New destination and transfer preparation from f4906f2

The first same-chat repair left a separate path for a newly claimed chat and for preparing a transfer to an unbound destination. It added the adapter to the running registry, placed the provisional profile in live settings and called the ordinary queued save. On the unmodified baseline the fixture observed a settings-file rename containing the destination after expiry while waiting for a writer, and after expiry, revocation, or source-owner generation change during the temporary-file write. A separate observation during an already authorized rename found the provisional destination visible to another settings caller.

The destination now uses a privately prepared queue adapter. A serialized settings operation builds its own candidate array, compares the expected entry and checks the exact chat, current proof, original name owner and adapter readiness. The same guard runs immediately before the temporary file is renamed. After rename completes the operation revalidates before changing live settings. Adapter installation and the binding or transfer offer are issued synchronously under that writer. A refusal after an authorized rename removes only the staged entry and restores the current settings before the next writer can proceed. An earlier unbound destination adapter remains active while the replacement is being prepared.

The HTTP MCP regression exercises a real unrelated save ahead of redemption and holds actual filesystem operations after writing a candidate temporary file or completing its rename. Before the guarded rename, expiry, revocation, and a changed owner each produced zero destination renames, bindings and transfer offers. Revocation after an authorized rename produced one destination rename followed by a compensating write. A concurrent node label and unrelated manual adapter survived. The exact mailbox history was preserved and no temporary settings file remained. A valid new claim succeeded; the existing explicit-transfer regression verifies the requested approval, destination, prior attachment and rejection of a repeated approval. The existing same-chat tests also ran. On macOS arm64 the targeted suites passed 93 tests with seven Windows-only skips and zero failures. TypeScript and scoped formatting passed. The tests used temporary local files and synthetic Desktop IPC and App Server responses. Installed-client acceptance was outside this run.
