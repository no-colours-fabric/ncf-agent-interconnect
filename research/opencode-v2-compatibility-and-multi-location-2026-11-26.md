# OpenCode v2 compatibility and concurrent project directories

26 November 2026. Design study for NCF Agent Interconnect. The product baseline is `v1.0.0` (`84cc4f8`). Local source checks used `d67fc40`. The goal is one bundled integration for the stable OpenCode 2.x series that preserves exact-chat delivery. The proposed protocol has not been implemented or tested end to end.

## Field reports and current behavior

On Ubuntu, OpenCode 2.3.0 loaded the same configured plugin for four project directories. In NCF v1.0.0 the node indexes the live bridge by setup target. A second live registration with a different boot identity retires the first and marks the entire generation ambiguous. Unloading a directory does not clear that marker. Registration maps this conflict to HTTP 401, and even `node_status` requires a successful bridge identity lookup. Opening several projects is normal OpenCode behavior. The reporter separately saw the version gate reject 2.2.5 and startup offer v1 for a v2 installation. [Issue 14](https://github.com/no-colours-fabric/ncf-agent-interconnect/issues/14) and [follow-up](https://github.com/no-colours-fabric/ncf-agent-interconnect/issues/14#issuecomment-7196052735). [Bridge registry](../desktop/core/opencode-v2-adapter.ts) and [MCP admission](../desktop/core/mcp-http.ts).

The owner's separate Debian-HSA report describes OpenCode CLI 2.3.2, a modified pin, a local mock model, and `codemode: false`. Two agents reconnected through approved transfers with history preserved, received text in the original session, woke the receiver, and transferred a file with matching SHA-256. The reported initial outage followed termination of the manually started NodeService. That report does not establish concurrent directory registrations, default Code Mode, Desktop behavior or support in the unmodified release. Keeping the node running addresses the reported Debian outage independently of issue 14.

NCF uses the literal `2.3.0` in the host guard, registration type, emitted registration and node validator. Changing only the guard can still advertise `2.3.0` for a different runtime. The plugin also validates the exact keys of the returned inbox item. A change in that shape matters after OpenCode may already have accepted the prompt. [Bundled plugin](../desktop/integrations/opencode-v2.ts) and [registration schema](../desktop/core/opencode-v2-adapter.ts).

## Contracts observed across 52 stable tags

Compared the official Git tags from `v2.0.0` through `v2.4.2` inclusive. This covered 33 tags in 2.0, five in 2.1, eight in 2.2, three in 2.3 and three in 2.4. For each tag, read the MCP call metadata writer, Promise plugin adapter, session and inbox schemas, event definitions, and the MCP transform and config interfaces. The table groups the changes relevant to this design. It describes source contracts, not a binary acceptance matrix. [First release](https://github.com/anomalyco/opencode/releases/tag/v2.0.0) and [last release inspected](https://github.com/anomalyco/opencode/releases/tag/v2.4.2).

| OpenCode stable tags | Host-generated MCP session key   | Creation time on the returned inbox item | Event handling                                                                       |
| -------------------- | -------------------------------- | ---------------------------------------- | ------------------------------------------------------------------------------------ |
| 2.0.0–2.0.3          | `_meta.sessionID`                | `timeCreated`                            | Unfiltered subscription. Cleanup and stream closure delimit the plugin lifetime.     |
| 2.0.4–2.0.5          | `_meta["ai.opencode/sessionID"]` | `time.created`                           | Same subscription and cleanup behavior. Public session locations omit `workspaceID`. |
| 2.0.6–2.1.4          | Namespaced key                   | `time.created`                           | Adds `location.shutdown`. The plugin still filters events locally.                   |
| 2.2.0–2.4.2          | Namespaced key                   | `time.created`                           | The Promise adapter forwards requested event types to the host.                      |

The first boundary changes both protocol fields in the same release. Version 2.0.4 also moved the HTTP wait endpoint under `/api/experimental`, while the Promise plugin kept `ctx.session.wait`. Depending on the plugin method avoids maintaining the HTTP path variants. The event subscription nonce must travel through the same stream as delivery evidence, even when the early host ignores the requested type list. [2.0.3 MCP metadata](https://github.com/anomalyco/opencode/blob/v2.0.3/packages/core/src/mcp/client.ts#L408), [2.0.4 metadata](https://github.com/anomalyco/opencode/blob/v2.0.4/packages/core/src/mcp/client.ts#L278), [2.0.3 inbox](https://github.com/anomalyco/opencode/blob/v2.0.3/packages/schema/src/session-inbox.ts#L55), [2.0.4 inbox](https://github.com/anomalyco/opencode/blob/v2.0.4/packages/schema/src/session-inbox.ts#L55), [shutdown event](https://github.com/anomalyco/opencode/blob/v2.0.6/packages/schema/src/location-event.ts), [2.1.4 subscription](https://github.com/anomalyco/opencode/blob/v2.1.4/packages/plugin/src/promise/adapter.ts#L334) and [2.2.0 subscription](https://github.com/anomalyco/opencode/blob/v2.2.0/packages/plugin/src/promise/adapter.ts#L336).

All 52 tags expose Promise plugin setup and cleanup, `ctx.mcp.transform`, session get/wait/prompt, an RPC event emitter, and the durable `session.inbox.delivered` event with session and inbox IDs. The prompt endpoint accepts a caller-assigned message ID, queue delivery and resume. The old and current sources therefore supply the primitives for one implementation with a small decoding layer. Behavioral equivalence still needs native acceptance. [2.0.0 plugin adapter](https://github.com/anomalyco/opencode/blob/v2.0.0/packages/plugin/src/promise/adapter.ts), [2.0.0 session admission](https://github.com/anomalyco/opencode/blob/v2.0.0/packages/core/src/session/session.ts#L139), [durable delivery event](https://github.com/anomalyco/opencode/blob/v2.0.0/packages/schema/src/session-event.ts#L201) and [2.4.2 plugin adapter](https://github.com/anomalyco/opencode/blob/v2.4.2/packages/plugin/src/promise/adapter.ts).

## Proposed integration

1. **Select the OpenCode major and negotiate the NCF protocol separately.** Allow stable major 2 into the compatibility handshake and register the actual `ctx.app.version`. Preserve the exact pinned fixture as a regression case. Version the new registration and routing contract explicitly. Keep the installed v1.0.0 plugin on its own wire contract during upgrade, and install the new asset through the existing owner-approved setup. A working plugin can report its observed version and a missing capability through an authenticated diagnostic registration before full activation. If the plugin never runs, the node can report only that it has not registered.
2. **Normalize at the host boundary.** Read either known session key only from host-supplied MCP metadata on the authenticated instance route. Reject conflicting values and missing session context on chat operations. Normalize both known creation-time shapes and validate the same session ID, assigned message ID, delivery mode and post-hook content. Keep changes to user-visible text or attachments significant. Check required methods before activation, then check the actual nonce round trip on the event stream. Apply local event-type and location checks in all versions. Use plugin cleanup and stream loss across the series, with scoped `location.shutdown` where available. A probe must never submit a test prompt into a user's chat.
3. **Route by the calling plugin instance.** Keep a registry keyed by `(targetId, generation, bootId)` inside the current node epoch. On authenticated registration, return a short-lived or revocable instance credential bound to that scope. The plugin uses its location's `ctx.mcp.transform` to update only the existing NCF server entry in memory. Give this effective entry a boot-specific URL and a credential header. Keep the target credential checks, tool names, permissions and on-disk config intact. Never put a secret in the URL. Bind each initialized MCP transport to that scope, check it again on tool calls, and retire only that instance on unload or disconnect. The bootstrap endpoint can expose minimal authenticated diagnostics before the transform takes effect. It cannot bind agents or release mailbox data. In OpenCode versions with connection pooling, the effective URL and headers already participate in the pool key. Startup order, reload and transport replacement require integration tests. [MCP transform API](https://github.com/anomalyco/opencode/blob/v2.0.0/packages/plugin/src/promise/mcp.ts), [location-scoped MCP service](https://github.com/anomalyco/opencode/blob/v2.0.0/packages/core/src/mcp/index.ts) and [2.4.2 pool key](https://github.com/anomalyco/opencode/blob/v2.4.2/packages/core/src/mcp/pool.ts#L50).
4. **Bind the exact session on that instance.** Verify the host-supplied session ID with `ctx.session.get`, the location, project and session creation identity. Check `workspaceID` wherever authoritative evidence exposes it. Since 2.0.4 the public session location may carry only the directory. A plugin can read sessions outside its own location. A directory match or a successful lookup alone cannot select a bridge. Use the authenticated origin of the tool call. If ownership is still ambiguous, block only that session. Pin all later bind, listen, submit and receipt processing to the selected scope. An identical registration returns its existing scope. A conflicting claim to the same active boot identity is rejected. Revoking a target generation retires every instance of that generation. Other locations continue. [OpenCode plugin location semantics](https://opencode.ai/docs/build/plugins/server#context) and [public location schema](https://github.com/anomalyco/opencode/blob/v2.0.4/packages/schema/src/location.ts).
5. **Keep dispatch and recovery semantics.** A successful prompt response establishes submission. Record native receipt only after both the matching post-hook inbox item and the correlated durable delivered event arrive for the current attempt, owner and epoch. Handle either arrival order. An interrupted issued attempt stays uncertain, with no automatic replay. A restarted node or host can re-register the transport with bounded backoff. A changed or unproven chat binding still requires the existing explicit transfer to retain history. Automatic restoration would require independently proven persistent ownership of the same session across boots. Restarting NodeService alone cannot resolve a routing or host-contract mismatch. [NCF binding implementation](../desktop/core/service.ts) and [delivery ledger tests](../test-desktop/opencode-v2-ledger.test.ts).

Expose configuration, node reachability, plugin registration, and per-session readiness separately. A target-authenticated `node_status` can give a limited bridge diagnostic when no instance is ready. Keep agent lists, history, attachments and binding operations behind their current authorization. Distinguish an authenticated instance conflict from a bad credential. Startup can use verified major-version evidence to select the v2 setup path and retain explicit selection for uncertain installations. Earlier project research covers the v1 switch and the separate permission migration. [Visibility study](opencode-v1-visibility.md) and [setup permissions study](opencode-setup-permissions.md).

## Validation and decision boundary

Two existing tests passed on the unchanged local product source with the isolated host fixture. One confirms the current second-instance failure, including loss of `node_status`. The other covers the rejected version guard and invalid registration. The first attempt hit a sandbox loopback restriction. Both passed with loopback available. These tests describe the baseline. No new adapter or live OpenCode host was run during this study. [Conflict test](../test-desktop/opencode-v2-context.test.ts) and [plugin tests](../test-desktop/opencode-v2-plugin.test.ts).

Before publishing support for all released tags, run an isolated real-CLI conformance smoke on each tag with a deterministic local model. Exercise the source boundaries on both sides (2.0.3/2.0.4, 2.0.5/2.0.6 and 2.1.4/2.2.0), the reported versions 2.2.5, 2.3.0 and 2.3.2, and 2.4.2 in the deeper suite. Include default Code Mode and direct tools, two sessions in one directory, two or four directories in one host, two processes sharing a profile and directory, an open sibling during unload, and a same-path workspace ambiguity. Test idle wake, busy queue, file hash, owner-approved transfer, node and host restart at the dispatch boundary, and native Desktop delivery on representative releases. Acceptance requires correct recipient, one admission and receipt per successfully delivered message, unaffected sibling routes, preserved history, and zero blind retries.

For future 2.x tags, reuse the same adapter when the observed contract fits. Distinguish **source-inspected**, **native-tested**, and **unverified** versions. An incompatible or unproven contract can still report diagnostics. Native delivery requires the evidence above. An unconditional guarantee for unpublished versions would require an upstream compatibility commitment or release-by-release verification.
