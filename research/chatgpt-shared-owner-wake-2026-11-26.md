# Shared-owner wake and automatic startup on macOS

### Unloaded-chat wake in the NCF adapter, 26 November

The target Mac configuration already had working active-turn admission. The shipping adapter used a desktop navigation callback for unloaded recipients even on the shared server. The earlier long-lived protocol client did not establish whether an NCF operation could disconnect immediately after resume without terminating the turn.

The isolated socket test runs a real private foreground server from the installed macOS arm64 ChatGPT 26.1120.50957, an independent client and a local gated model. The short-lived client resumed the exact chat and disconnected immediately. The independent client observed the queued message in a new running turn, then observed that turn complete after the model gate opened. The target history contained the complete ordinary item once and the queue contained no copy. Another previously loaded chat contained no matching item. An initial attempt that passed the long socket alias directly to Node returned ENOTSOCK; using the actual short private socket behind that alias allowed the handshake.

Experimental source commit `fa9af9d745e785216cd3331a4b88bed9092d72c6`, parent `f5a2f92`, implements this path in CodexQueueAdapter. The change operates on the shared-server connection. When NCF observes its durable pending attempt, the adapter checks the head's original client ID and complete payload hash, the current binding and the unloaded thread, then requests metadata-only resume. An unrelated head, including one with identical text under another ID, or an edited payload cannot authorize a wake. The wake does not resend the message or create a receipt. It leaves admission to the existing matching native-history projection. Listing the queue and resuming are separate server operations; this trial does not prove atomic ordering against a concurrent GUI queue edit.

| f5a2f92 baseline, navigation callback recorded without opening a GUI                       | Requested navigation, recipient remained unloaded, exact item remained queued, no receipt.                                                                                                                   |

The fixture reconstructed the adapter; this does not test full NCF application restart or enumeration of attempts from the live hub database. |

The trial driver takes the absolute bundled CLI path, `--short-lived-wake` and `--adapter=<absolute path to codex-queue.ts>`. Use `--expect-queued` for the baseline. The normal queue suite passed on macOS with 21 passing and three Windows-only skips; typecheck and formatting passed. No installed application or active owner profile was modified. The owner-facing GUI, its focus, and a normal Windows launch are distinct acceptance checks.

Both adapter scenarios were repeated on the final commit with `--gui`. In each case the GUI witness opened the original signed ChatGPT application through LaunchServices in a hidden instance with separate user data. The instance reported a connected local WebSocket transport before the test. A different control chat remained in its original running turn before and after the recipient completed. The receiver was unloaded at the start, the test model received the complete ordinary item, the native queue was empty for its ID, and the adapter recorded one receipt. No desktop navigation callback was invoked. The test recorded protocol state and the GUI's transport log; it did not inspect an on-screen tab or operate the owner's production profile. An initial control sampled the turn list before model generation had started and saw a transient interrupted status. The final fixture waits for the independent model request before it takes the control snapshot.

The isolated branch also passed the ordinary NCF application source build. Both GUI witness cases passed again when importing the actual compiled `build/core/codex-queue.js` instead of the TypeScript source. No installer was created or installed.

### Normal macOS launch from a previously running opener

The isolated LaunchServices publication check launched a background probe through the same long-lived NSWorkspace process four times. That process started before publication and never had the variable in its own environment. The probe saw no value initially, saw the new value after publishing a unique harmless test key in the current user's Aqua launchd domain, saw it in an explicit positive control, and saw no value after withdrawal. No ChatGPT endpoint was published and no working GUI was restarted. Together with the previous signed-ChatGPT selection tests, this verifies the OS propagation step for a one-time NCF-managed setup. A fresh launch of the actual installed GUI by the owner's normal icon with NCF-managed publication is still unverified.

The isolated startup-order fixture opened a signed, disposable ChatGPT instance with a previously established endpoint while its server was absent. The GUI selected WebSocket and transitioned through connecting, error and disconnected. Compatible foreground service startup at the same endpoint did not produce a connected event in the original GUI during the observation. Another isolated signed GUI started later connected to the same ready server. This gives a positive control for the endpoint and does not establish indefinite retry behavior.

With `--activate-on-connect`, a private same-user listener existed before the GUI started, while the vendor server did not. The original GUI's connection triggered startup of the vendor server; the fixture forwarded the local stream to that instance. The original GUI reported a connected local host. This used a private Unix socket in a disposable profile, a same-UID peer check, no TCP and no configuration or repair of the working desktop. An initial shutdown generated ENOTCONN on half-close after the client had already exited; handling that normal peer-exit condition produced a clean repetition. The proof covers backend activation after the GUI has opened. It assumes that the front listener is available, and does not install or prove OS login registration. Normal startup should arrange that listener before publishing its address.

An end-to-end run with `check.mjs --short-lived-wake --on-demand-gui --adapter=<compiled module>` combined this launch route with the actual compiled NCF adapter from fa9af9d. For both a fresh submission and a pending attempt restored to a new adapter, the signed scratch GUI triggered backend startup, NCF woke the exact unloaded chat on that backend, the local model saw the full message and its turn completed. One native copy, zero remaining copies in the queue, one NCF receipt and zero navigation calls were observed. The separate control chat remained in its original in-progress turn. The fixture supplied the listener and the authorized dispatch; it did not install a login service, change production client configuration or measure UI tab selection.

In a further native case, `--launchd-gui` temporarily registered a private socket in the current user's launchd domain. The OS held the socket while the helper and vendor App Server were stopped. The first connection from a new instance of the signed ChatGPT application activated the job, which received the descriptor through `launch_activate_socket` and started the vendor server. Both fresh and restored NCF dispatch cases passed on the compiled adapter with the same assertions, including the separate chat still running. The fixture removed its launchd job and waited for helper shutdown after each run. Permanent installation, login after reboot and activation from the owner's Dock icon have not been exercised. No setting or service was left enabled for the owner's ChatGPT.

### Windows handoff and portable model

The Windows operator reported that the original signed desktop client (MSIX 26.1120.6357.0) initialized and issued thread RPCs on the same isolated vendor App Server as the NCF test client. The control client created the only identified chat. The desktop requested sign-in in that first empty profile. No target turn or visible tab was verified. The combined Windows source revision 9965ba8c (e20548d plus the wake change) passed 31 targeted resolver and queue tests.

The local model fixture and smoke test let a researcher hold or release a reasoning stream in a newly generated profile. On macOS, the CLI bundled with ChatGPT accepted the complete marker, issued a reasoning delta and returned the exact assistant text in the original completed turn. A separate read of the account state in the same trial configuration returned `requiresOpenaiAuth: false` and no account. The [desktop gateway guide](https://learn.chatgpt.com/docs/enterprise/connect-to-a-gateway) documents provider selection and starting a new chat. Availability of those UI actions in this signed-out build remains to be tested. Windows received the portable model archive (SHA-256 f0fdb46ed29877cbb9a9f78a7e517249048c7502b2c0f569bebf7b793214d5ef).
